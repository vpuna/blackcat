A check looks at a system on a schedule and tells the owner when it stops working, with an optional automatic fix. Use one when the owner says things like "keep checking that the website is up and restart it if not" or "tell me if a container on the server stops". (A check looks at a system. Keeping a list of things from the owner's messages is a watch, which is something else.) Always add `--json`:

    blackcat check add <name> [--run '<command>'] [--file <path> [--max-age 20m]] [--look-for "<what working looks like>"] [--fix '<command>' [--tries 2] [--wait 90s]] [--every 30m] [--alert now|briefing|"after 3"|"after 15m"] [--quiet 03:00-03:30] [--remind 1h] --json
    blackcat check edit <id or name> [--run …] [--file …] [--max-age …] [--look-for … | --no-look-for] [--fix '<command>' | --no-fix] [--tries …] [--wait …] [--every …] [--alert …] [--quiet … | --no-quiet] [--remind … | --no-remind] [--name …] [--pause | --resume] --json
    blackcat check list · show <id or name> · run <id or name> --dry-run · remove <id or name> --json
    blackcat check snooze <id or name> [-n <number>] [--for 4h | --until-fixed] --json      (no length: until tomorrow morning)
    blackcat check unsnooze <id or name> [-n <number>] --json
    blackcat check fixed <id or name> --json      (the owner fixed it: looks now, and again over a few minutes)
    blackcat check fix <id or name> --json        (runs its fix again now, and looks)

- **Ask a plugin when one can answer.** A plugin that looks after a system has a `check` command of its own, which succeeds only when that system is well: `blackcat ha check <name> --is <state>`, `blackcat unifi check`, and so on (each plugin's section says if it has one). Make that the `--run` of the check, rather than working out for yourself how to tell. The plugin knows; the check asks on a schedule.
- How it decides: `--run` is a shell command, and a non-zero exit means not working (`systemctl is-active camera`; for another machine, `blackcat ssh run nas 'docker inspect -f {{.State.Running}} media | grep -q true'`). `--file` with `--max-age` fails when the file has stopped changing. If `--look-for` is given, an assistant with no tools then looks at the image (or the command's output) and judges it against that description. Use the plain rules wherever they are enough: they cost nothing. The description is only for what needs eyes.
- Write `--look-for` to describe what a healthy result looks like right now, not what the thing is supposed to be for. Look at the current evidence first (open the image with Read, or run the command) and say what you see. A description that doesn't match the healthy state causes false alarms and needless restarts.
- Turn the owner's words into a concrete plan and show it before creating anything: what is looked at, what counts as working, the exact fix command, how many tries, how often. Then run the command. The owner gets an approval prompt showing it in full, because a check runs its commands by itself from then on and its fix runs without asking. Creating one gives the fix command a standing permission, which the owner can remove in /permissions (the fix then stops, the check carries on).
- Creating or changing a check looks once straight away and returns the result as `tested`. Always tell the owner that result. If it did not pass, the check is created paused and its fix is not run: say so, give the reason, and work out with the owner whether the check is wrong (correct it with `check edit`) or the thing really is down. The fix command itself is never test-run; say that it is untested until the first real failure.
- Prefer the least powerful fix: restart the one service, never reboot. Never add a fix the owner didn't ask for.
- What a check finds wrong is kept one entry an outage (a "finding"), from when it was first found until it works again: `check show <check> --json` gives `now` (what is wrong, numbered 1, 2, …) and `before` (past outages, how long each lasted). A check with a description can find several separate things at once; each is its own finding.
- The owner is told when a finding starts (or as `--alert` says: after some looks in a row, after it has lasted a while, or only in the briefing), not in its `--quiet` time, again every `--remind` while it stays so, and when it works again. Not on every run. After a fix has failed, it is not tried again for that finding; `check fix` runs it again when the owner asks.
- **When the owner says they know, or asks you to ignore something a check found, snooze it: `check snooze`.** Never change the check's `--look-for` to list what to ignore: that is permanent, and it is the owner's description of working. A snooze lasts until a time (`--for`, or tomorrow morning) or `--until-fixed`; the finding stays on record, and the owner is told again if it is still so when the snooze ends, or when it works again. With several things wrong, give `-n` (from `check show`).
- When the owner says they fixed something, use `check fixed`: it looks, and tells them whether it works.
- For a known daily disturbance (a nightly backup or update), suggest `--quiet` for that time, or `--alert "after 2"`, rather than a snooze every day.
- **"blackcat itself"** is a check that is always there: it runs `blackcat activity problems`, plain rules over blackcat's own activity record (no model), and each thing it finds is a finding of its own. It cannot be removed or made to look at something else; it can be paused, renamed and told when to speak (`--every`, `--alert`, `--quiet`, `--remind`). When the owner asks why one of its findings is there, look at the record (`blackcat activity recent`, `usage`, `show`) and explain it.
- A `--run` command can report several separate things itself: exit non-zero and print `{"problems": [{"key": "…", "title": "…"}]}`. Each becomes a finding of its own, with no model asked.
- Each look with a description uses a little of the owner's plan, so don't set `--every` shorter than needed (15 to 30 minutes is usually right).
- `run` without `--dry-run` looks for real: if it is not working and the fix is permitted, the fix is run. Use `--dry-run` to only look.
