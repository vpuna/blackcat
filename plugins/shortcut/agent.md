When the owner asks in words for something one of these does ("send me the sky image"), run that shortcut first, before any other way you know of doing it: `blackcat shortcut run <name> --json`, then send each of its `files` with `[[send: <path>]]` and pass on its `output`. The shortcut is how the owner set that task up, and it stays right when things move to another machine.
When the owner asks you to "build a /x command" or "make a shortcut for…", work out the steps, then create it:
    blackcat shortcut add <name> --description '<text>' [--run '<command>']... [--send <file>] [--caption '<text>'] [--reply output|none] --json
- A shortcut can have **actions**: a word after its name with steps of its own (`/waves pause`, `/waves stop`). Add one with `blackcat shortcut action <name> <action> --run '<command>' [--description '<text>'] --json` (it makes the shortcut if there is none; `--remove` takes an action away). A shortcut with actions and no steps of its own is a menu: `/waves` then shows what it has. `--main` turns a shortcut's own steps into an action (`shortcut action waves play --main`). Run one with `blackcat shortcut run <name> <action> --json`. Use actions when the owner wants one name for several related things (play, pause, stop); a different thing altogether is another shortcut.
- Use `{dir}` for files a step fetches: it is a private folder for that shortcut, and files there can be sent. To get a file from another machine: `--run "blackcat ssh get <host> '<remote path>' {dir}/<name>" --send {dir}/<name>`.
- To have one sent to the owner by itself ("send me /temps every morning at 8", "the sky picture at 19:00 on weekends"): `blackcat shortcut schedule <name> [<action>] --cron "<minute hour day-of-month month day-of-week>"` for a repeating schedule (cron, local time: 08:00 on weekdays is `0 8 * * 1-5`; repeat `--cron` when one expression is not enough), `--once "YYYY-MM-DD HH:MM"` or `--in 2h` for one time only ("send me the sky picture on Friday at 21:00"), and `--off` to stop. `add` takes the same `--cron`. The reply says the schedule back in words: check it is what the owner asked for, and tell them. Times are local, 24-hour. One action can be sent by itself: name it after the shortcut (`blackcat shortcut schedule waves play --cron "0 22 * * *"`). When the owner wants something a shortcut or one of its actions already does to happen at set times, schedule that; do not make a new shortcut for it.
- "Do X, but only if Y" ("play the rain at 22:00 unless something is already playing", "restart it only if it is down") is possible: a schedule has no condition of its own, so the condition goes in a step. Write one step that tests and then acts: `<test> && <command>` to act when the test passes, `<test> || <command>` to act when it fails. A test is any command that succeeds or fails: a plugin's `check` command (`blackcat ha check "<thing>" --is playing`, `blackcat allsky check`, `blackcat unifi check`) or a shell test. Make it an **action of the shortcut it belongs to** (`blackcat shortcut action waves night --run 'blackcat ha check "<speaker>" --is playing || blackcat shortcut run waves play'`), not a new shortcut, then schedule that action. Try the test by itself first so you know which way it answers, and tell the owner what the action does in each case.
- Each step must end by itself and succeed on its own; steps run in order and stop at the first failure. Prefer blackcat's own commands to raw shell.
- Creating or changing one needs the owner's approval, which shows the recipe. It is tried once when created: tell the owner the `tested` result, and if it failed, why.
